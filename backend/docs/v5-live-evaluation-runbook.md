# v5 真实数据评测运行手册

## 2026-08-31 执行复盘

### 发生了什么

在 9 条 nonprod 简历/JD 的 v5 生成与盲评任务中，案例 2 连续暴露结构化输出截断、证据 scope 错挂、计划预算越界、安全回退重复和语义 Judge 误报。执行过程中采用了“修改代码后立即重跑完整案例”的方式，缺少全局调用、Token、耗时和重试熔断，最终形成高成本的修复—重跑循环。

案例 1 虽完成，但使用安全回退，且双顺序盲评不一致；案例 2 未完成；案例 3–9 未运行。完整 Harness 审计显示共启动 38 次 v5 workflow，仅 1 次成功、37 次失败；发出 279 个物理 Provider 请求，收到 271 个响应，合计约 347.1 万输入 Token、99.4 万输出 Token。案例 2 同一输入完整重跑 32 次且 0 次成功，案例 1 重跑 6 次仅 1 次成功。该结果不能视为一次有效的九例评测。

### 根因

1. 运行器没有全局和单案例预算，只设置了单次 workflow 超时。
2. 失败案例没有阶段级检查点，任何修复都从证据抽取重新开始。
3. 检查点只看文件是否存在，没有实现版本、输入摘要和配置指纹校验，可能混用不同代码版本结果。
4. 没有案例筛选和 canary 模式，调试案例 2 时仍通过九例入口启动。
5. 将真实 API 实跑同时用于发现缺陷、修改实现和验收，缺少离线回归夹具。
6. 对单例失败连续调参，未设置“同一失败连续出现即停止复盘”的执行纪律。
7. P09 自然语言 Judge 的结论未先做服务端一致性校验，导致明显自相矛盾的误报进入阻断逻辑。
8. 部分即时修复可能针对单个案例过拟合，需要在恢复实跑前独立审计和补测。
9. 并行 P01/P02 和 P01 chunk 没有首错共享取消，一条分支失败后其他在途请求仍可能继续计费。
10. P12 双顺序评测缺少统一 Harness、预算与取消上下文。
11. P01 以 12 个 block 固定分片，未结合 64k 上下文、16k 结构化输出空间和真实字符量；仅约 7.7k 字符的简历被拆成 24 次基础抽取调用。
12. 运行器虽限制外层尝试次数，但 OpenAI 兼容 SDK 的默认内部重试未关闭，可能出现预算记一次、网络实际请求多次的不可见重试。
13. 案例 3–8 使用同一份源简历但不同 JD，旧运行没有带实现与 Provider 指纹的可信 P01 缓存，重复支付相同证据抽取成本。
14. 并发分支首错后仅触发取消，没有等待其他在途请求完成结算就写失败状态，可能造成报告中的调用数和 Token 仍在变化。
15. 输出目录采用“先检查为空、后创建文件”的非原子流程，两个进程可能同时通过检查并混写同一批次。
16. 运行脚本无参数时默认进入真实 case 2，而不是只做离线预检；真实调用缺少显式、醒目的启用开关。

### 禁止带入正式链路的即时修复

以下类型的改动必须撤回或改为可证明的确定性实现，不能用来让样本“通过”：

- quote/span 无法定位时把整个 source block 晋升为该模型事实的证据；
- 把漏抽取 block 自动创建为 `source_supported` EvidenceAtom，从而制造虚假的高覆盖率；
- 仅凭继承标题启发式改变项目/工作的业务 scope；
- 根据 Judge 的自然语言措辞或“看起来像误报”把事实 error 降为 warning；
- 在缺少合法核心证据时用身份、隐私或 JD-only 内容满足覆盖率。

## 强制执行规则

1. 真实数据批量运行前必须先通过类型检查、v5 全量测试和单例 canary。
2. canary 默认只允许运行一个案例；未经新的显式扩容，不得自动进入剩余案例。
3. 每次运行必须同时设置：最大模型调用数、最大输入 Token、最大输出 Token、单案例墙钟时间和全局墙钟时间。
4. 任一预算达到上限时立即停止，不继续当前案例的后续阶段，不自动进入下一案例。
5. 单案例失败一次即停止批次并生成失败摘要；禁止在同一进程内无限重试。
6. 修改 Prompt、Schema、Validator、证据归属或工作流后，已有检查点全部视为失效；最终九例必须在全新目录、同一实现指纹下运行。
7. 检查点必须校验输入 SHA-256、工作流版本、Validator 版本、Prompt 版本集合、运行器协议版本和评测配置摘要。
8. 调试期间不得以完整九例入口反复运行；使用明确的案例筛选参数。
9. 真实 API 只用于已通过离线回归的验证，不用于无上限探索式调参。
10. 每次恢复前先汇报已有调用与 Token；达到预设预算后必须回到用户确认点。
11. 不得为了让样本通过而降低事实门禁。服务端只能驳回可机械证明为矛盾的 Judge 结论，并必须有测试覆盖。
12. 批量结果只有在 9 条均使用同一实现指纹、同一配置完成时才可发布；混合版本结果必须标记无效。
13. 同一 `inputDigest` 最多允许两个完整 run；第二次仍失败必须停止并复盘，不能继续真实 API 调参。
14. 所有并行模型任务必须共享父级取消信号，并在首个失败时取消同组在途请求。
15. 没有 Harness 物理请求计数、预算预留、超时和取消信号的外部模型调用不得进入批处理。
16. 预算运行必须直接调用目标 Provider，显式设置 SDK `maxRetries=0`；备用模型、SDK 隐式重试和整案自动重跑均禁用。
17. P01 分块必须保留完整经历/项目范围，并根据输入与结构化输出容量设置上限；分块计划、并发数和版本必须进入实现或缓存指纹。
18. 同源简历跨 JD 复用 P01 时，只允许进程内 factory 创建的可信缓存；命中后仍须重跑严格 Schema、完整文档 Validator 和 EvidenceBundle 完整性校验，任何篡改直接阻断而非静默重算。
19. 真实运行必须显式提供 `--live` 和全新输出目录；无参数和 `--dry-run` 均不得初始化 Provider、创建输出或发出外部请求。
20. 真实运行在写任何状态前必须原子获取目录独占锁；崩溃遗留锁不得自动抢占，必须人工确认原进程停止后处理。
21. 首错时先触发共享取消，再等待所有已预留请求完成成功或失败结算，最后才写失败状态与部分报告。
22. 进程内 P01 缓存不得被当作可恢复的持久检查点；恢复若会重复提取已完成案例的同源简历，必须阻断而不是重新外呼。

## 推荐运行阶段

1. **离线阶段**：固定失败夹具，运行类型检查和所有 v5 测试，不调用外部模型。
2. **Canary 阶段**：只运行案例 2，使用低预算与失败即停，验证完整生成和双顺序盲评。
3. **一致性阶段**：清空到新的输出目录，从案例 1 开始运行；不复用历史混合版本产物。
4. **批量阶段**：逐案保存，任一失败停止；完成后才计算整体胜率和同源岗位差异度。
5. **发布判断**：同时审查事实门禁、安全回退率、盲评顺序一致性、相对质量、差异度、调用数、Token 和延迟。
