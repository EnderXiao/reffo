## 1. 目标与不变项

核心价值：Reffo 不是通用简历打磨器。它首先需要理解目标岗位究竟要解决什么问题，什么样的人能够在其业务环境和约束下完成任务、产生预期结果；再从用户的真实经历中找到最有说服力的胜任证据，组织成专门面向该岗位的简历。

“把一份通用简历从 60 分润色到 90 分”不是核心目标。目标是让招聘方更容易判断：**为什么这位候选人的这些经历，与这个岗位真正要完成的工作有关。** 表达质量是必要条件，岗位理解和针对性证据组织才是差异化价值。

全链路的主分析关系为：

**业务环境与约束 → 岗位任务 → 绩效目标与成功条件 → 候选人属性 → 简历证据 → 定向选材与表达。**

这里的“岗位成功画像”是基于 JD 的可解释工作假设，不是对企业真实内部需求的全知判断；“候选人画像”不是人口特征、人格标签或理想人设。JD 决定观察角度和内容优先级，源简历决定能够声称什么。

好简历应同时回答：适合什么工作、处理过什么问题、个人承担什么、形成什么价值、哪些内容值得面试验证。优化目标依次包括：

1. 岗位理解：识别任务、结果、成功条件和用人优先级，区分 JD 明示信息、合理推断与未知项。
2. 胜任证据匹配：区分做过相似工作、具有可迁移经验、仅有弱信号和暂无信息，不能靠工具名相同就认定胜任。
3. 定向表达与辨识度：围绕本岗最重要的问题组织个人贡献、方法、交付与结果，保留真实职业特点。
4. 信息利用率：充分解释简略材料已有的职业含义；没有数字时利用行动、交付、复杂性和问题解决过程。
5. 叙事与阅读：有主线、有取舍、一条一个重点；摘要解释已有经验的岗位相关性，不复读正文或写评审意见。
6. 可信与可解释：允许专业化表达，保留数字、归因、阶段、否定与不确定性的真实边界。
7. 工程稳定性：通过确定性编排、有限调用和可恢复检查点减少失败及重复消耗。
8. 可验证价值：证明不同目标岗位会得到有依据的不同选材与表达，不能用通用写作分上涨代替岗位针对性。

保持不变：对用户的 Markdown/JSON 框架、既有顶层响应字段、输入授权范围、原始材料留存与隐私边界。内部写作契约可以版本化升级；不得在对外结构不变的名义下继续强迫新 Writer 服从只能逐字复制的旧契约。

不做：恢复 P08/P09 互审循环、增加多个自由讨论的写作 Agent、全量搬运源材料、逐条强套 STAR、强制每条量化、把 JD 或行业惯例变成个人经历。画像是内部分析工具，不把六类属性变成对外新增的六个简历栏目，不为每一类属性强凑正文。

## 2. 产品分析模型与本次优先级修正

上一版方案的重点是解除 P06D 只能拼接原文的限制；这一工程问题仍然需要解决，但只改 Writer，最多得到更好读的通用简历，不能保证更懂目标岗位。

已有默认路径仍保留 P01 → P02 → P03 → 代码策略与选材 → P06D → 本地交付决策；新 Writer 作为非生产选项处于验证中。P12 是离线评测，P05 默认由代码执行，P09 不回到正式链路。已有局部单测与历史回放不是本次 JD 驱动方案的验收记录，继续实施前需要重新冻结具体版本。

本版修正上一版“先优化成文，P02 视情况再改”的优先级：**先让 P02 形成岗位成功画像，再让 P03 建立胜任证据关系，随后由代码选材和 Writer 把关系转化为定向简历。** 不假定已有 P03 关键词关联已经足以承担这一职责。

### 2.1 三层内容，以业务环境和约束作为解释背景

| 分析层 | 必须回答的问题 | 输出原则 |
| --- | --- | --- |
| 岗位任务 | 服务谁、处理什么对象、完成哪些动作、与谁协作 | 拆成可理解的任务单元，不把一个 JD 段落机械等同于一个任务 |
| 绩效目标 | 完成任务最终要产生什么结果，什么才算做好 | 区分交付物、业务结果、质量要求；JD 没给数值就不补 KPI、预算或期限 |
| 人才属性 | 哪些知识、技能、经验、能力、行为方式及动机适配更有助于完成任务 | 属性必须关联任务或明确要求，不输出泛化的“全能优秀人才”清单 |

业务背景包括产品/服务对象、业务阶段、主要协作方、资源或合规约束、工作条件等。明示的内容保留来源；推断的内容标注依据与不确定性；没有依据则留空。不能凭公司名、职位名或“互联网企业”等标签补出组织文化、增长压力、用户规模、汇报关系或技术栈。

JD 不一定完整、准确或内部一致。分析结果可以是部分画像，不能为了填满三层结构虚构信息。

### 2.2 六类候选人属性：分析维度，不是六项强制认证

| 属性维度 | 企业想判断什么 | JD 常见信号 | 在源简历中寻找什么 |
| --- | --- | --- | --- |
| 知识 | 是否理解必要专业领域 | 熟悉用户增长、财务知识、计算机基础 | 工作或项目中的领域应用，相关课程、资格等；仅有术语不等于掌握 |
| 技能 | 是否掌握完成任务的方法与工具 | SQL、Figma、Python、访谈或建模 | 使用对象、操作方法、交付物及用途；工具列表和实际运用分开 |
| 经验 | 是否处理过相似场景和任务 | 相关年限、ToC、从零到一、行业经历 | 问题、场景、职责、业务阶段、规模和结果的相似性，不只看标题 |
| 能力 | 能否在复杂条件下解决问题 | 数据分析、项目推进、跨部门协同 | 本人判断、取舍、行动与交付，如何处理依赖或限制；不靠形容词认证 |
| 行为特征 | 工作方式是否适应任务要求 | 责任心、沟通、自驱、严谨 | 可观察的行为片段，例如发现问题并跟进解决；不从文风推断人格 |
| 动机与适配 | 是否愿意做，并适应必要工作条件 | 岗位兴趣、使命认同、出差或现场要求 | 用户明确表达的兴趣、偏好和条件；未提供则未知，不自动补“认同使命、抗压性强” |

“发展潜力”作为跨维度观察：用真实的学习应用、职责拓展、问题迁移等迹象说明可能性，不凭年龄、名校或名企经历判定，也不把潜力写成已经具备的高级经验。

学历、年限、工具和关键词既可能是资格要求，也可能是识别胜任属性的信号：保留 JD 明确的资格要求及其状态，但不能把信号当作能力本身；也不能因为有可迁移能力就默默宣布满足明确缺失的必要资格。

### 2.3 四个招聘判断及其可判断边界

1. **能不能做**：哪些知识、技能和能力已有支持，支持强到什么程度。
2. **有没有做过**：是否有相似业务情境、任务、本人动作、交付和结果；相似在哪里、差异在哪里。
3. **愿不愿意做**：只根据用户表达的动机和偏好判断；工作年限、跳槽频率或一句自我评价不能证明忠诚、兴趣或未来稳定性。
4. **是否适合在这里做**：把适配拆成可讨论的工作方式与现实条件，例如跨时区协作、必要出差；不做笼统文化人格打分，不用性别、年龄、婚育、健康等个人特征代替岗位相关证据。

四个判断均允许“部分支持”或“当前未知”。简历可以重点回答前两项，并在用户已明确表达且适合写入时呈现后两项；不能强迫一页简历证明所有适配问题，更不能输出录用概率或保证能稳定达成绩效。

### 2.4 从任务到证据的完整例子

JD 原句：`负责会员增长策略并推动跨部门落地。`

| 环节 | 合理分析 | 不应补入的内容 |
| --- | --- | --- |
| 任务 | 制定会员增长策略；协调相关方推进实施 | 假设必须管理某个具体团队或使用某套软件 |
| 目标 | 会员增长方向明确；具体增长口径和目标数值未知 | 自行设定收入增长 30%、季度新增会员目标 |
| 成功条件 | 合理推断需要识别增长问题、设计方案、处理协作依赖并跟进实施 | 把假设的归因体系、完整实验流程写成 JD 明示要求 |
| 属性 | 增长分析、方案设计、项目推进和协同；相关业务经验有助于判断适用性 | 强加未提及的年限、SQL 硬门槛或人格标签 |
| 证据 | 寻找相似项目、本人动作、交付、协作情境；规模及量化结果有则保留 | 因源简历没有数字，就虚构增长结果或判定没有价值 |
| 表达 | 有会员增长经历则优先呈现；只有其他业务的协作落地经验，则突出该真实经验的可迁移部分 | 把其他业务的项目名称和成果改成会员增长项目 |

如果原文只有“参与活动需求整理，和研发沟通排期”，可以写“参与活动需求梳理与研发排期沟通，支持需求对齐和实施安排”。这能支持部分协作与执行经验，不能写成“制定会员增长战略并驱动业务增长”。定向优化改变的是选择和表达，不是经历归属。

## 3. 合理扩充策略：表达可以展开，具体经历不能凭空补齐

需要分开两种推断：对 JD 的推断用于建立“这个任务可能如何成功”的工作假设；对简历的展开用于解释“这个人已经做过的事情有什么职业含义”。前者可以决定去寻找哪些证据，不能成为后者新增个人经历的来源。

| 层级 | 允许行为 | 正文处理 |
| --- | --- | --- |
| 事实重述 | 去冗词、改语序、规范术语、拆句、合并同主题事实 | 直接使用，保持原义与限定 |
| 职业含义展开 | 解释已知行动的对象、用途和可迁移价值，不新增具体工作事件 | 可以使用；写成用途或职责含义，不写成已实现效果 |
| 合理但未确认的经历假设 | 猜测可能使用的工具、流程、方法、交付物、协作机制 | 只作为独立可选补充建议，不混进投递正文 |
| 新增实质主张 | 数字、客户、项目、年限、证书、职位、主导关系或业绩 | 只有真实材料支持时才能使用 |

示例：

- 源文：`负责产品需求整理，和研发沟通。`
- 可写：`负责产品需求梳理与研发沟通，支持团队理解需求重点。`
- 可询问：是否形成过需求清单或 PRD？具体负责哪个环节？
- 不可直接补写：`独立输出 PRD，主导三轮迭代，效率提升 30%。`

再如，“参与访谈”可表达为“具有用户访谈参与经验”，不能提升为“独立主持研究”或“精通用户研究”。“获批晋升”不能改成“已经履任”；“为上线提供准备”不能改成“已上线取得增长”。

不让用户逐个确认普通润色措辞。只有补充后会实质改变能力主张的信息才值得提问，建议最多 3 个高价值问题，允许跳过。沿用已有补充建议载体，不新增强制表单或流程阻断；源材料本身无法形成任何可用内容时，应明确说明不足而不是凑字数。

补充问题按“是否能改变核心岗位判断”排序，而非按空字段数量排序。例如，核心岗位强调跨部门推进时，询问实际协调了哪些角色、本人解决了什么问题；不默认要求用户补 KPI。明确且影响投递决策的出差等条件，可询问意愿，跳过后保持未知，不擅自承诺。

## 4. 自适应写作与新增质量维度

JD 信息充分度、源材料充分度、职业阶段、岗位距离分别判断，不能用一个“稀疏”标签决定全部策略。岗位距离依任务、场景和成功条件评估，不由职位名称差异直接决定。

| 材料或场景 | 写作策略 | 避免 |
| --- | --- | --- |
| 表达简略但有真实工作 | 展开职业含义、说明职责环节、突出已有交付 | 将短材料视为弱能力，或补造标准工作流程 |
| 经历确实有限 | 写清实践、方法、执行、学习和具体产出 | 自封专家、硬造商业收益 |
| 材料丰富冗杂 | 围绕岗位挑选代表事实，合并重复，保留连贯时间线 | 项目越多越好、全量证据必须进入正文 |
| 转岗或岗位距离较大 | 展示相似问题与可迁移能力，真实缺口另行说明 | 把 JD 改写成候选人经历 |
| 资深或管理职责明确 | 突出判断、复杂性、责任和组织贡献 | 只堆执行动作，或无依据升级所有权 |
| JD 简略或主要是招聘套话 | 使用明示任务形成保守的部分画像，降低推断权重 | 从“自驱、抗压”推演一套具体业务或全能画像 |
| JD 内部矛盾或条件不清 | 保留冲突与未知，优先不矛盾的任务，必要时给可跳过的澄清建议 | 擅自选择最方便生成的解释，或因画像不完整阻断全部生成 |

额外纳入以下维度：

- 业务语境：写清为谁、处理什么问题、工作对象是什么；背景不详时不编市场、客户或业务规模。
- 个人辨识度：选择该候选人真实的方法、取舍、交付和职责环节，避免泛化模板。
- 贡献成熟度：区分研究、方案、试点、上线、验证与规模化，而不是统一写“落地”。
- 面试可展开性：正文能引出具体问题，且候选人有依据解释；不输出臆造的面试故事。
- 阅读与机器解析友好：栏目稳定、层次清楚、日期和术语一致、真实岗位词自然出现；不承诺某个 ATS 分数或筛选结果。
- 语言与职业阶段适配：按输出语言和明确职责调整语气，不从年龄、性别、姓名或学校/公司名气推断能力。

### 5.1 P02：岗位成功画像的内部契约

建议工作代号为 `job-success-profile-v1`。这是设计建议，不是当前已有 Schema；恢复实施后应先核对现有类型，再确定最小迁移方案。不要将结构化画像塞进旧 `normalizedRequirement` 或长篇 rationale 字符串，造成下游只能再次猜测。

最小对象及关系：

| 对象 | 必需表达的信息 |
| --- | --- |
| `context` | 已知业务对象、场景、阶段、协作与约束；未知项单列 |
| `tasks` | 任务 ID、对象与动作、关联结果、优先级、JD 来源 |
| `outcomes` | 交付或预期结果、明示指标及其口径；没有明示数值时为空 |
| `successConditions` | 做成任务所需的条件及与任务的关系，区分明示和推断 |
| `attributes` | 六类之一、关联任务/成功条件、具体内涵、希望看到的证据类型 |
| `requirements` | 原有要求引用、必要资格/偏好/待判断条件，以及 AND/OR 等明示关系 |
| `unknowns/conflicts` | 未知、模糊、冲突点，以及对画像判断的影响 |

每项可判断信息保留 JD 的 `sourceBlockId/span` 或原要求引用，并标注 `explicit / inferred / unknown`；推断给一句简短依据和置信等级，不输出长推理过程。派生属性同时链接其上游任务，不能只有一个模糊来源标签。未知项不编造引文。

优先级区分 `core / supporting / optional / unclear`，来源类型和优先级分别表达：JD 未明说但任务强相关的能力可列为推断的核心成功条件，却不能升级为企业明示的硬门槛。只有清楚表达的必要资格才进入必要条件状态；“优先”“加分”“例如”和替代选项不能被代码统一提升为必需。

模型负责语义拆解，代码负责 ID、来源存在性、合法关联、去重和可计算统计。初版可用“最多约 5 项核心任务、1–3 条主要成功路径”控制摘要长度，其余明确要求保留索引，不用硬截断丢掉重要条件。少任务 JD 不凑满数量，复杂 JD 不强行压成单一人物模板，允许存在多种可胜任的能力组合。

岗位来源与简历来源在类型和引用空间上分开：JD 引用只能支持岗位判断，不能放进 Writer 的个人事实 `evidenceIds`；推断的业务指标、任务和属性不能混入候选人事实视图。这一分离由代码保证，不依赖模型自行记住来源边界。

P02 只读取 JD，不读取候选简历来反向降低岗位要求。P01 与 P02 的输入独立，已有授权和预算允许时可并行；P03 必须等待两者完整验证后再运行。

### 5.2 P01：建立可写事实视图，不破坏原始证据

在现有 EvidenceAtom 之上增加内部展示/写作视图，保留原始证据不变：

- 业务内容：对象、行动、交付、结果，以及明确出现的方法。
- 受保护信息：数字与单位、角色归因、阶段、否定、时间、不确定性。
- 编辑说明：核验记录、资料等级、投递建议，不进入简历正文。
- 定位信息：源文档、scope、block/span、原始证据引用。

先处理可由明确边界和既有规则可靠分离的内容；混合句无法可靠分离时保留限定或转为待处理，不用宽泛正则删除“不确定”等关键词。若必须改变抽取契约才能正确分离，再单独升级 P01、使相关缓存失效并纳入冷缓存预算，不能偷用旧缓存掩盖抽取变化。

### 5.3 P03：把画像转成胜任证据地图

建议增加 `job-fit-map-v1` 内部对象，复用原有合法证据 ID，不重新生成事实或重复输出全部原文。每条映射说明：目标任务/成功条件、属性、证据 ID、支持状态、相似点、关键差异、拟表达角度。

支持状态至少区分：

- `direct`：有相似任务与情境的具体实践；不要求岗位名称相同。
- `transferable`：问题结构、方法或协作方式相似，但行业、对象、规模或职责深度不同；写清可迁移部分和差异。
- `weak_signal`：仅有课程、技能列表或笼统自述，能够提供线索但不足以证明完成复杂任务。
- `unknown`：材料未提供，不等于没有能力或不愿意做。
- `explicit_gap`：来源明确支持存在差异，例如要求现场工作而用户明确只接受远程；与未知分开。
- `conflicted`：材料矛盾或解释不能确定，不强选有利版本。

知识、技能、经验、能力可以由同一项目支持，但不能把这四个标签重复计成四份独立经历；同样，不用“具备某属性”的判断替换真实项目证据。一次成功交付不自动证明能够在所有环境稳定复现。

输出 1–3 条有依据的胜任主线，例如“相似业务问题的直接实践”“其他场景中的可迁移推进经验”。同时保留岗位缺口、证据缺口和表达缺口三类差异：真实经历不足不能靠 Writer 修复，已有经历表述不清才是润色重点。

角色动机、组织适配和行为方式只标注实际证据支持的范围。合理推断的 JD 属性与薄弱简历信号组合，不能变成“已证实匹配”。现有对外匹配分保持接口兼容，但其说明必须保留未知和推断范围，不输出虚假的精确胜任概率。

### 5.4 P05：由岗位核心任务驱动选材，与成文解耦

代码计划定义“章节—目标任务/成功条件—胜任主线—主题—核心事实—可选事实—长度预算”。每个业务主题能解释它服务哪个岗位判断；必要时间线、教育等基础信息不必强行关联任务。

选材按以下顺序执行，不以词频作为主分数：先选有支持的核心任务证据，再考虑直接性/可迁移性、本人贡献清晰度、具体交付或结果、与岗位约束的相似性；最后在篇幅内去重并保留职业连贯性。特别强的可迁移证据可以优于同岗位名但空泛的职责描述，不将 `direct` 标签当作无条件胜出。

核心事实是经选择的关键贡献，不是把所有原始证据标成必用。篇幅是软目标，避免为了最少条数拆碎，或为了最多条数把不同主题硬并。优先覆盖“有可用证据的核心任务”，对没有证据的任务记录缺口，不制造对应正文。

摘要允许综合多个经历中有支持的优势，由专用摘要规则处理；不得顺便合并项目归因、累加未经证明的年限或拼成一个虚构成果。正文仍保持经历与项目的归属边界。

同主题关系消费新版 P03 的任务—证据语义关联，代码负责稳定分组、同 scope 边界与容量分配。关键词重合仅可作为低权重辅助，不假定相同工具、相同名词或同一宽泛能力标签就代表同一业务主题。

同一份简历针对不同 JD，应可能改变摘要重点、展开/压缩的经历、同一经历内的条目顺序和表达角度；真实职位、时间线、项目性质、数字和贡献归属保持一致。相近 JD 得到相近内容是正常现象，不为差异而改写；对任务明显不同的 JD，只更换标题则视为定向失败。

### 5.5 单次 Writer：消费定向写作计划，不重新发明候选人

Writer 输入仅包含：本岗核心任务与成功条件的紧凑摘要、各项是明示还是推断、与候选人有关的胜任主线、计划槽位和选定事实。不重复 P02/P03 的全量账本，不让 Writer 再做一遍画像、评分和选材。

每段只返回必要字段：计划标识、正文、支持证据引用。元数据、顺序、统计、账本和外部响应由代码生成，避免模型重复输出整套事实档案。

引用说明文本的依据，不是“语义已经被证明”的证书。代码可以检查结构、引用、数值及部分明确冲突，不能因此宣称任意改写已被完整验证。新 Writer 必须先在非生产和人工审阅范围验证，再逐步扩大允许表达范围。

替换 P06D，不在 P06D 后再增加一个润色模型。原 DSL 保留为诊断与版本回退路径，不把未经质量确认的原文拼接稿伪装成高质量成功交付。

### 5.6 版本、兼容和暂停后的衔接

- 本版优先变更区域：`evidence.ts`、`schemas.ts/types.ts` 中岗位与映射契约，P02/P02R、P03/P03R，以及代码选材和 Writer 输入适配；具体文件在恢复实施时核对。不能只改 Markdown Prompt 而保留无法承载画像的旧契约。
- 内部新增画像/映射可通过兼容投影继续返回既有 JD 分析、匹配、简历字段；不把画像六维、推断记录或审计账本写进简历正文。用户是否能看到独立画像页是另一个产品需求，本方案不默认新增页面或 API 顶层字段。
- 旧 P02/P03 结果不冒充新版画像结果。恢复检查点必须校验输入、阶段契约、提示词、模型配置及上下游依赖哈希；P02/P03 升级时使相应下游缓存失效。
- P01 不因 JD 变化而重新抽取，前提是其自身语义依赖未变且缓存有效。如果共享 Schema/编译器改动使当前实现中的 P01 缓存键失效，先审计依赖边界，不能手工改摘要哈希强行命中；必要冷缓存成本另行说明。
- 保留已有 Writer、本地回放和引用检查作为可复用基础，不宣称它们完成本版上游升级。旧版与新版的评测标准、代码及产物各自冻结，新增验收口径单独版本化。

## 6. 三个关键阶段的提示词核心

以下是设计核心，待内部契约及代码适配后落地；本轮不修改运行时 Prompt，不可直接粘贴进当前只能 `emit_atom` 的 P06D。

### 6.1 P02：理解岗位如何成功

> 你是岗位分析师。分析对象不是关键词清单，而是：在 JD 描述的业务环境和限制下，这个岗位需要完成哪些任务、产生什么结果，什么条件与候选人属性有助于做到。
>
> 先梳理业务对象、任务和目标，再关联成功条件与知识、技能、经验、能力、行为特征、动机与适配。六类属性是检查视角，不要求每类都有结论；只保留与任务或明确要求相关的内容。区分核心任务、辅助要求和偏好，允许多种合理的胜任路径。
>
> 每项判断区分 JD 明示、基于任务的合理推断和未知。保留来源及简短依据；不虚构业务阶段、KPI 数值、公司文化或隐藏门槛，不把“优先”改为“必须”。职位名、学历、年限和工具是信号或条件，不等于能力本身。
>
> 只输出当前画像契约。不要查看候选人后反向调整岗位画像，不写候选简历，不调用其他 Agent 审核。

### 6.2 P03：找到胜任关系，而不是制造匹配

> 你是岗位与经历的匹配分析师。以岗位任务和成功条件为锚点，寻找候选人真实材料中的场景、本人行动、方法、交付和结果，说明它们支持什么岗位判断。
>
> 区分直接实践、可迁移实践、弱信号、未知、明确差异及冲突。可迁移关系应说明相似的问题结构和不能迁移的部分；同工具不等于同能力，同职位名不等于同经历。不要把材料没写解释为本人不会，也不要将能力缺口伪装成可润色解决的问题。
>
> 形成少量有依据的胜任主线，并为核心任务推荐代表证据。行为方式用实际行动支持；动机、文化与现实条件只采用用户明确提供的信息，不推断人格、忠诚或稳定性。
>
> 只返回版本化映射、引用及简短理由，不重复整份原文，不写最终简历，不新增数字、业绩、工具或职位。

### 6.3 Writer：把胜任关系写成这份岗位的简历

> 你是面向当前目标岗位的简历主编。你的任务不是生成一份通用高分简历，而是依据岗位成功画像、候选人的胜任主线和代码写作计划，让招聘方理解：候选人哪些真实实践说明其有望完成这个岗位的重要工作。
>
> JD 决定观察角度，源简历决定事实。优先呈现与核心任务及成功条件有关的经历和个人贡献；相似经验突出直接支持，可迁移经验写清其真实工作对象和作用，不改成目标岗位的经历。不要重新推演岗位画像或为了匹配填满所有属性。
>
> 优先呈现岗位相关问题、个人行动、具体方法、交付与结果。材料简略时充分解释已有工作的职业含义和用途；材料丰富时做取舍。没有数字时使用真实实践和交付，不强造结果，不要求每条具备完整 STAR。
>
> 每条围绕一个主题，写清工作对象与个人贡献。摘要以本人的职业陈述概括最相关的经验方向和已有优势，不写“候选人、值得面试、可迁移至某岗位”等评审意见，不复制正文或堆 JD 关键词。保留真实特点，避免“优秀、赋能、全面负责”等缺乏内容的套话。
>
> 允许等义改写、规范术语、去冗词、拆句和同主题重组。可以解释已知职责的用途，不能新增具体工具、流程、交付物或成绩；工作目的不等于已经实现的收益，团队成绩不等于个人独立完成。保护计划所标注的数字、归因、阶段、否定和时间边界。
>
> 不把行业惯例、岗位要求或合理猜测写成个人经历，不补“认同公司使命”“能长期稳定任职”等未提供的承诺。缺少信息时优先写好已知内容；必要补充建议使用独立载体，不在正文写待确认、材料等级或核验口吻。
>
> 遵循既定栏目和篇幅目标，以重点完整和自然可读为先，不凑条数和字数。只返回当前版本写作契约要求的字段，不输出推理过程、统计账本或额外报告。

### 6.4 Prompt 工程规则

正向任务目标在前，少量必要边界在后；按当前 JD/材料类型选 1–2 个短示例，不把所有行业模板与对抗样例同时塞入请求。六类属性共用一套紧凑契约，不各起一个分析 Agent。属性与任务的关系用 ID 表达，原文只在来源目录保留一份；禁止复制长 rationale。以冻结输入检查“画像—选材—正文”是否一致，不用 Prompt 长度或关键词数量判断质量。

## 7. 门禁、失败处理与成本控制

### 7.1 门禁分层

- 硬阻断：非法结构、空成品、未知引用、明确跨经历归因、可确定的受保护事实变化、隐私或内部字段泄漏等可被代码明确定位的问题。
- 质量提示：略短、非关键事实未使用、没有量化、未达到推荐条数、一般措辞或风格问题。普通质量提示不得再次通过交付层被一律变成硬阻断。
- 岗位画像与匹配不确定性：JD 没写绩效数值、属性不齐全、用户动机未知、某任务只有可迁移证据，均不单独阻断正常生成。明确不满足的岗位条件可在已有匹配说明中如实呈现，但不是系统技术失败，也不是补造经历的理由。
- 需审阅风险：自由改写中代码无法可靠判断的语义变化。不得一概当错，也不能一概视为事实已证实；在非生产/灰度阶段通过人工审阅、离线抽检和限制写作操作范围校准风险。

基础可用性与美化目标分开：真实存在展开章节却没有有效内容，可以阻断；合法的一行任职时间线不是空章节。材料短并且确实只足以形成少量内容时，不强迫其达到通用最低条数。

### 7.2 单向编排与有限失败处理

采用代码驱动的单向阶段流程，保留 P01 的有界并发、稳定序号、完整性屏障及可信检查点。流式事件用于进度展示，不把半份抽取结果交给下游写作；恢复只重跑缺失或失效阶段。

结论：流式本身不会解决乱序或质量问题。稳定性来自代码掌握依赖、排序、状态和预算，不来自让多个 Agent 自由接力讨论。

默认只进行一次正文模型调用，不因风格警告重写，不恢复 P08/P09 循环。顺序、统计和纯格式问题本地修复；确有硬错误且能局部恢复源支持表达时，仅在整篇仍完整可用的前提下替换该段并重新执行本地检查。不能通过删掉关键内容交付残缺稿。无法可靠处理时明确终态，不递归外呼、不伪装成功。网络/抽取阶段沿用现有有界重试，和“为了质量重写”分开计数。

### 7.3 预算

- 单分片常规路径仍以 P01、P02、P03、一次正文生成共 4 次为目标；N 个 P01 主分片为 N+3 次，不含现有有限修复及按需 P04。
- 命中完整可信 P01 缓存时，常规生成目标为 3 次。写作升级不得偷偷增加一轮 Agent 审核。
- P02 在原本一次岗位调用中输出画像，不另外增加“画像 Agent”；P03 在原本一次匹配调用中建立胜任关系，不再独立做六维互审。现有修复/策略调用是否触发，继续记录在有界预算中。
- P03 接收紧凑画像、可匹配事实及必要限定，不重复整份抽取账本。Writer 只接收与选材有关的画像摘要、胜任主线及事实。P12 保留原始 JD 和足够核验材料，不能只读模型画像，否则可能把 P02 的误解当成评分真值。
- 每个阶段发送前预检上下文和额度，保存实际调用数、输入/输出 Token、延迟和缓存条件。估算不是账单，未知消耗必须单列。
- 新 Writer 会输出正文而非短 DSL，先在现有额度下测试并压缩传输冗余；如确需重新分配阶段额度，单列方案和预算审批，不默认调高流程总上限。完整性不能以截断正文换取。
- P12 只在冻结版本评测或抽检时按预算运行，不随每次生成自动调用。真实简历和 JD 外发另按既有授权范围执行，不因本方案获得无限调用授权。
- 加入画像并不保证 Token 自然减少。P02/P03 升级先做无外呼的大小预检，分别记录本阶段增量和下游压缩量；超过现有额度时先简化重复传输，若仍需扩大或重新分配预算，先说明并另行授权，不偷偷提高总上限。

## 8. 分阶段执行与退出条件

| 阶段 | 主要工作 | 交付物与退出条件 |
| --- | --- | --- |
| 0：重新冻结产品基线与验收口径 | 固定 Case3 与多 JD 输入、历史稿/当前稿、Prompt/代码/预算；人工标注核心任务、推断边界和应呈现证据 | 原七维与数值门槛不降低；新增岗位画像/定向能力指标在看新结果之前冻结，旧结果不换标签冒充新标准成绩 |
| 1：P02 岗位成功画像 | 先实现画像契约、来源关联与必要条件语义；改 P02/P02R、解析器、缓存依赖及兼容投影 | 在完整、简略、套话、冲突 JD 上完成本地契约与标注回放；能追溯任务—目标—条件—属性，推断不成为硬要求；外部结构不变 |
| 2：P03 胜任映射与代码选材 | 实现直接/可迁移/弱信号/未知/明确差异；岗位任务优先的主题计划；复用事实视图 | 有核心任务对应的具体引用、映射理由与差异；无证据任务不凑正文；同一简历在不同 JD 下计划有合理区别，事实和时间线一致 |
| 3：单次 Writer 定向成文 | 接入紧凑画像摘要和胜任主线，调整 Writer Prompt 与兼容渲染；延续分层本地校验 | 合成与历史响应回放通过；未知属性不阻断；没有 P08/P09 循环，正常路径不新增一次调用；本地回放不代替新版模型实测 |
| 4：Case3 与小规模多 JD 实测 | 预检后按新授权运行真实 Case3；逐条核对画像、映射、成品；再测试少量已授权的同人不同岗组合 | Case3 链路通过、内容完整且服务真实 JD；明确每个主要选材决定的依据；有同标准人工评审和实际成本记录，失败先归因再决定重试 |
| 5：泛化验收与白名单灰度 | 至少 100 份真实黄金案例、30 份对抗输入；包含分层及同人不同岗测试；真实招聘人员评审后才扩大范围 | 同时满足通用质量门槛和岗位定向能力门槛；分组无未处理重大问题，有监控、停止和回退条件 |

阶段 4 的 Case3 成功不代表普遍上线，更不能单独证明“一岗一简历”。多案例外发均需数据授权与预算确认，不能把已有 Case3 单轮授权扩展到全部目录。开发集和最终验收集按候选人隔离：同一人的另一个 JD 配对不应一部分用于调优、一部分冒充未见验收样本；同人多岗可以作为固定的成组测试，不能按独立候选人夸大样本量。

目前用户指定目录只提供部分资源，已盘点为 10 个主体目录、27 组可直接读取的文本配对；不等于 100 名真实候选人，材料真实性、验收使用范围及独立招聘评审记录仍需确认。未经最终验收不启用生产默认路径。

回退使用上一版经过质量验收的版本；如尚无合格线上版本，则保持内部测试或停止扩大开放，不把已知低质量 DSL 稿默认定义为可上线回退。提示词、内部契约、策略、校验器和相关缓存依赖一起版本化。

## 9. 质量评估与上线门槛

### 9.1 评估方法

保留现有七维评分上限 25/20/15/10/10/10/10，分别对应事实可信、岗位针对性、选材、重要事实召回、职业连贯、阅读简洁和可投递性，避免本轮一边改变权重一边宣称涨分。

其中“岗位针对性”评价是否回应真实核心任务与成功条件；“选材”评价是否挑选最能支持本岗判断的经历；“重要事实召回”针对人工事先认定的岗位相关关键贡献，而不是覆盖所有原子。保留权重，但将新解释锚点单独版本化；按新锚点比较时旧稿和新稿必须重新同场评审，不能直接拼接历史分数。

在固定输入条件下评价材料表达质量；候选人实际缺少某类经历另记岗位距离，不能全部计为写作失败。没有量化不自动低分，长不自动高分，弱匹配不等于虚构。

新旧稿必须用同一冻结标准同场比较，历史稿来源未确认时不标为 V4。不同 P12 版本、不同画像或不同评分锚点的分数不能直接证明生成改善。P12 用双顺序处理位置偏差，但两次同模型评分不等于两位独立专家。

评审输入提供足够的源材料定位；指控必须有实际成品短摘录和对应来源。代码确认摘录确实存在只能消除部分误报，仍不能证明评语语义正确。缺少对照时标为无法核验，不能等同已证实新增；这类稿件也不能冒充已完成事实验收。

由真实人工招聘评审独立判断质量，Case3 与关键争议案例至少双人复核，重大分歧裁决；不能由同一模型扮演两名专家冒充人工结论。人工和模型评测费用分别列入预算。

评估拆为三层定位责任，而不是只给最终稿一个总分：

1. **岗位理解是否正确**：招聘人员先看原始 JD，独立标注核心任务、明示约束、合理推断和未知，再核对 P02。不能用 P02 自己生成的画像作为唯一真值。
2. **胜任关系是否成立**：对照原简历与独立岗位标注，判断 P03 的直接/可迁移关系和未选证据。源简历没有证据与系统漏选已有证据分别计数。
3. **成品是否表达了关系**：看核心证据是否进入正文、本人贡献是否清楚、选择与顺序是否服务目标 JD，而非只检查引用 ID 被使用。

沿途指标用于离线归因和发布决策，不增加在线模型门禁。P02 理解错了应修正上游，不能把同一个误解反复交给 Writer 润色；P03 正确但正文没有体现，则定位到选材或表达。

### 9.2 保留的基础质量与工程门槛

以下沿用上一版目标，不因产品重心调整而降低，也不是已取得的成绩。冻结记录保持原样，新增岗位画像口径另建版本；不得看完新结果再修改门槛。

| 指标 | 建议目标 |
| --- | --- |
| 重大事实错误、隐私或审计信息泄漏 | 验收集中为 0；发现即暂停扩大使用并追因。零观测不代表总体零风险 |
| 链路成功率 | 真实黄金集首次有效生成率至少 95%；现有有界恢复后至少 98%，不新增正文互审循环；分开报告提供商失败和产品失败，不能只算成功稿 |
| 人工可投递率 | 全部真实测试案例中至少 90% 无需实质重写；生成失败计入分母。语法/措辞微调与事实/结构重写预先定义 |
| 质量分 | 成功生成稿的人工七维评分中位数至少 80/100，并单列失败和低分尾部；不以分数覆盖事实失败 |
| 相对基线 | 同场盲评新稿胜率至少 60%、负率不高于 10%，平局单列；记录样本量与不确定性，不以 Case3 单例胜出替代总体比较 |
| 关键贡献保留 | 对人工确认、无冲突且在篇幅范围内应呈现的核心事实不得遗漏；不以覆盖所有原子代替质量 |
| 预算与延迟 | 同模型、同输入、同缓存条件下，流程 Token 中位数与 P95 不高于冻结基线；P95 延迟不回归，且所有运行受预设调用上限约束；若质量成本存在取舍须显式评审 |

30 份对抗输入用于验证冲突、长 scope、混合说明、数字限定、注入、碎片和异常格式的处理。应拒绝的恶意或不可用输入要安全结束，不把“必须生成成功”当成对抗集指标。所有指标按材料充分度、岗位距离和职业阶段分组，防止均值掩盖某一类用户体验差。

### 9.3 新增的岗位定向能力验收

以下是本版提出的新增目标，在阶段 0 由产品负责人和招聘评审冻结口径后用于新验收集；本轮不修改已冻结的运行时验收常量，不据此重算已有成绩。它们是离线发布条件，不是让单个用户输出再次陷入重试的门禁。

| 指标 | 建议目标及判定方式 |
| --- | --- |
| 核心任务识别 | 对人工预先标注的核心任务，召回率（正确识别数/应识别数）与查准率（正确识别数/识别总数）分别至少 90%；合并同义任务后统计，不能靠多列任务刷召回；JD 过简的样本单列 |
| 明示与推断分离 | 来源伪造、将画像推断当成企业明确必要条件、将“优先/或”变成“必须/且”的重大误判为 0；未知项不按解析失败计算 |
| 胜任映射准确性 | 人工认可的直接/可迁移关系占全部这两类关系至少 90%；只看关键词而实际不支持的关系算错误，弱信号不得冒充直接证据 |
| 核心任务的证据利用 | 在人工确认“源材料确有可用证据且应在篇幅内呈现”的核心任务中，成品实际表达相关贡献的比例至少 90%；分母由人工标注，不由模型通过少选任务缩小 |
| 同人不同岗的可辨识针对性 | 在至少 20 个候选人组、每组至少 2 份核心任务明显不同的真实 JD 中，盲评正确归属目标 JD 的比例至少 80%；同时说明具体选材/侧重点依据，只有职位名或关键词替换不算成功 |
| 跨 JD 的事实一致性 | 同一源简历生成的不同版本中，新增或篡改职位、时间、项目性质、数字、贡献归属的重大问题为 0；合理省略和侧重点变化不算矛盾 |

没有可评映射、没有来源可用证据的样本记录“不适用”和数量，不能计为 100% 正确；样本不足或缺少人工记录时状态为未验收，不能取零值冒充通过。报告样本量、分层结果及不确定性，同人多 JD 的置信区间按候选人分组计算，不把相关样本当作独立用户。

同人不同岗实验的目标是验证定向价值，不是要求两份简历文本差异越大越好。隐藏目标标签、显式目标职位抬头等可直接泄题信息；不删改真实历史职位或必要内容；评审必须指出正文如何服务目标任务。对近义 JD 或只是换公司名的 JD，不采用这一归属指标，转而检查内容稳定性。

### 9.4 最小实验组合与失败归因

| 实验 | 应观察到的行为 | 要排除的问题 |
| --- | --- | --- |
| 同一简历，任务明显不同的两份 JD | 选材、摘要重心或经历内顺序有证据支持的差异 | 通用稿换标题、套用两套关键词 |
| 同一 JD，业务经历不同的两位候选人 | 各自使用真实且不同的胜任主线，缺口如实保留 | 所有人都被写成同一个“理想候选人” |
| JD 同义改写、条目调序、增加无关套话 | 核心任务与选材大体稳定 | 被关键词频次和 JD 顺序牵引 |
| 职位名称相同、任务不同；名称不同、任务相近 | 前者能区分任务，后者能识别可迁移关系 | 单纯职位名匹配 |
| JD 缺少 KPI、用户缺少动机信息或量化结果 | 形成部分画像，利用现有行动与交付继续写作 | 补造 KPI、承诺意愿、把未知当不合格或技术失败 |
| 仅改变姓名等与工作无关的个人信息 | 岗位画像和胜任判断不改变 | 以个人属性代替职业证据 |

实验可以先用合成数据验证契约和逻辑，但合成数据不计入真实黄金集。真实 A/B 优先在同一 JD、同一候选人、同模型与缓存条件下比较冻结基线和新版，再做同人多 JD 定向实验。新增外呼次数和人工评审费用单列预算，不因实验设计获得无限测试授权。

## 10. 最终决策摘要

Reffo 的核心是“理解岗位要怎样的人、为什么需要这些属性，再找到这个人真实经历中最有说服力的回应”，而非单纯追求更漂亮、更长或更高通用评分的简历。

明确分工：

- P02 从 JD 建立任务、绩效目标、成功条件和六类属性之间的关系，保留推断与未知。
- P03 把岗位成功画像与真实经历连接，识别直接胜任、可迁移价值、弱信号和缺口。
- 代码选材把核心岗位判断落实为写作主题和证据优先级；Writer 在这些依据内完成专业、自然、有针对性的表达。
- 代码负责结构、归属、调度、预算、可确定的风险以及稳定交付。
- 用户只补充会实质影响能力判断的信息，不确认每个普通措辞。
- 离线模型评审辅助定位问题；真实招聘人员评价岗位理解、胜任关系和可投递质量，二者都不形成线上反复重写循环。

调整后的实施顺序：**冻结 JD 驱动验收标准 → P02 岗位成功画像 → P03 胜任证据映射与代码选材 → 单次 Writer 定向表达 → Case3 和小规模同人多岗实测 → 泛化验收与灰度。**

此前 Writer 改动是可复用的成文基础，不再是独立推动的主线。当前暂停执行，先按本版方案对齐后续实现；完成文档修订不等于授权自动恢复代码修改、真实外呼或上线。
