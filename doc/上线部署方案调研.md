# Reffo 上线部署方案调研

调研日期：2026-07-10

## 结论

推荐分两阶段上线：

1. 非生产和正式后端使用不同 API 域名，分别绑定 `.env.nonprod` / `.env.prod`，后端进程启动时固定连接对应 Supabase project。
2. Taro H5 部署为静态站点，前端只选择后端 API 域名；Supabase URL、Publishable key 和 Storage bucket 由后端 `GET /api/v1/system/public-config` 返回，避免前端 API 域名和 Supabase project 错配。

当前最适合 Reffo MVP 的平台组合是：

- 后端：Render Web Service + Docker，按环境分别注入 Supabase 配置。
- 前端 H5：Render Static Site 或 Cloudflare Pages。
- 域名和 HTTPS：平台托管证书，前端域名和 API 域名分离。

选择 Render 作为后端优先方案的原因是：仓库已有 `backend/Containerfile`，后端需要常驻 HTTP 服务。Render 官方支持 Docker 部署、环境变量、健康检查、自动部署、静态站点和域名证书，MVP 阶段工程改造较小。

## 当前项目上线形态

### 后端

- 技术栈：Bun + Elysia + TypeScript。
- 启动命令：`bun run src/index.ts`。
- 默认端口：`PORT=3000`，监听 `HOST=0.0.0.0`。
- 健康检查：`GET /api/v1/mvp/health`。
- OCR 配置检查：`GET /api/v1/parse/health`。
- 前端公开配置：`GET /api/v1/system/public-config`。
- 数据库：本地开发可用 SQLite；非生产和正式环境使用各自独立 Supabase project。
- 必需密钥：`OPENAI_API_KEY`。
- OCR 密钥：`GLM_OCR_API_KEY` 或 `GLM_API_KEY`，缺失时服务可启动，但 OCR 接口返回 `OCR_CONFIG_MISSING`。

### Taro H5

- 构建命令：`corepack pnpm@10.33.2 build:h5`。
- 构建产物：`frontend/Taro/reffo-taro/dist`。
- 前端通过 `REFFO_ENV=local|nonprod|prod` 选择默认 API 域名，也可通过 `API_BASE_URL` 显式覆盖。
- 前端不直接配置 Supabase URL 或 Publishable key；运行时从后端 public-config 获取。

### RN / 小程序

RN 和小程序不建议作为第一阶段上线目标。它们需要单独处理应用签名、包构建、商店或小程序审核、真机回归和平台域名白名单。第一阶段先上线 H5，RN / 小程序进入后续发布链路。

## 方案对比

| 方案 | 后端 | 前端 | 数据持久化 | 优点 | 风险 |
| --- | --- | --- | --- | --- | --- |
| A. Render 一体化 | Render Docker Web Service | Render Static Site | Render Persistent Disk | 一个平台管理，配置少，适合当前 SQLite MVP | 挂磁盘后单实例，部署期间会有短暂停机 |
| B. Render + Cloudflare Pages | Render Docker Web Service | Cloudflare Pages | Render Persistent Disk | 前端 CDN 更强，预览部署方便 | 跨平台环境变量和域名配置多一点 |
| C. Railway 一体化 | Railway Service | Railway 静态或服务 | Railway Volume | 开发体验简单，Volume 也支持 | Volume 同样限制副本，长期生产仍需托管 DB |
| D. Fly.io | Fly Machine | Cloudflare Pages | Fly Volume | 区域和容器控制强 | 运维门槛高于 Render，不适合当前最小上线 |
| E. 云厂商生产化 | Cloud Run / ECS / K8s | CDN / 对象存储 | Cloud SQL / RDS | 扩展性和合规能力最好 | 当前阶段改造和运维成本最高 |

## 推荐架构

```text
用户浏览器
  |
  | https://app.reffo.app
  v
Taro H5 静态站点
  |
  | REFFO_ENV=prod -> https://api.reffo.app/api/v1
  v
后端 Bun/Elysia 容器服务
  |
  | DATABASE_PROVIDER=supabase
  v
Supabase prod project

后端外部依赖：
- DeepSeek/OpenAI-compatible API
- GLM-OCR API
```

## Render MVP 落地步骤

### 1. 后端 Web Service

服务类型：

- Runtime：Docker。
- Root Directory：`backend`。
- Dockerfile Path：`Containerfile`。
- Docker Command：使用镜像内 `CMD`，即 `bun run src/index.ts`。
- Health Check Path：`/api/v1/mvp/health`。
- Region：优先选靠近目标用户和模型 API 的区域。
- Instance：MVP 可从小规格开始，OCR 和 LLM 调用主要瓶颈在外部 API 延迟。

持久化磁盘：

- Mount Path：`/app/data`。
- 原因：当前 `Containerfile` 的 `WORKDIR` 是 `/app`，代码写入相对路径 `data/reffo.sqlite`，因此挂载 `/app/data` 可以保留 SQLite 文件。
- 限制：挂载磁盘后只能单实例，部署会有短暂停机。该限制可接受于 MVP，但不是长期生产解法。

### 2. 后端环境变量

必填：

```text
OPENAI_API_KEY=<DeepSeek 或兼容 OpenAI API Key>
OPENAI_BASE_URL=https://api.deepseek.com
AI_MODEL=deepseek-chat
HOST=0.0.0.0
PORT=3000
CORS_ORIGIN=https://app.reffo.app
APP_ENV=prod
DATABASE_PROVIDER=supabase
AUTH_REQUIRED=true
SUPABASE_PROJECT_ENV=prod
SUPABASE_URL=<prod Supabase URL>
SUPABASE_PUBLISHABLE_KEY=<prod Publishable key>
SUPABASE_SECRET_KEY=<prod Secret key>
SUPABASE_STORAGE_BUCKET=user-files
```

OCR：

```text
GLM_OCR_API_KEY=<GLM OCR Key>
GLM_OCR_MODEL=glm-ocr
OCR_TIMEOUT_MS=150000
OCR_MAX_FILE_SIZE_MB=10
```

可选：

```text
AI_FALLBACK_MODELS=
PROMPT_VARIANT=v1
GLM_OCR_BASE_URL=
GLM_OCR_ENDPOINT=
```

### 3. Taro H5 静态站点

Render Static Site：

```text
Root Directory: frontend/Taro/reffo-taro
Build Command: corepack pnpm@10.33.2 install --frozen-lockfile && corepack pnpm@10.33.2 build:h5:prod
Publish Directory: dist
```

Cloudflare Pages：

```text
Root Directory: frontend/Taro/reffo-taro
Build Command: corepack pnpm@10.33.2 install --frozen-lockfile && corepack pnpm@10.33.2 build:h5:prod
Build output directory: dist
```

如果平台默认 Node 版本不满足 Taro 构建，需显式设置 Node 22。可以通过平台环境变量或构建镜像完成。

### 4. 域名

建议：

- `app.reffo.app`：H5 静态站点。
- `api-nonprod.reffo.app`：非生产后端 API。
- `api.reffo.app`：正式后端 API。

后端 `CORS_ORIGIN` 只允许生产前端域名，不建议生产使用 `*`。

### 5. 首次上线 smoke

后端：

```bash
curl https://api.reffo.app/api/v1/mvp/health
curl https://api.reffo.app/api/v1/parse/health
curl https://api.reffo.app/api/v1/system/public-config
```

H5：

1. 打开 `https://app.reffo.app`。
2. 上传或粘贴源简历。
3. 粘贴 JD。
4. 触发生成。
5. 确认生成结果页、历史卡片、刷新后历史数据可用。
6. 检查浏览器 Network 中 API 域名、CORS、响应码和错误提示。

## 当前必须补的代码和配置缺口

上线前建议先完成这些小改动：

1. 修正 `backend/Containerfile` 的 lockfile 复制规则。当前仓库实际是 `bun.lock`，但文件里写的是 `bun.lockb*`，Docker 构建可能拿不到锁文件。
2. 新增 `.dockerignore`，排除 `.git`、`data/`、`node_modules`、日志和临时产物，避免把本地 SQLite 或缓存打进镜像。
3. 将数据库路径改为可配置，例如 `DATABASE_PATH=/app/data/reffo.sqlite`，保留默认值兼容本地。
4. 后端补一个更轻量的系统健康检查，例如 `/healthz`，只验证进程存活；业务健康继续用 `/api/v1/mvp/health`。
5. CI 增加部署前质量门禁：
   - `cd backend && bun test ./src`
   - `cd frontend/Taro/reffo-taro && corepack pnpm@10.33.2 exec jest --runInBand --no-watchman`
   - `cd frontend/Taro/reffo-taro && corepack pnpm@10.33.2 build:h5`
6. H5 构建时显式传入 `REFFO_ENV=prod`，或用 `API_BASE_URL` 覆盖默认 API 域名。
7. 建立生产密钥清单和轮换策略，禁止把 Secret key 写入前端构建环境；Supabase public 配置由后端 public-config 下发。

## 生产化演进

MVP 上线后，下一步应继续强化 Supabase 生产治理：

- 数据库：完善 Supabase migration、备份、RLS 回归和正式变更流程。
- 文件：完善 Supabase Storage 清理策略、上传审计和文件生命周期管理。
- 鉴权：完善用户注册、邮件确认、正式测试账号和账号恢复策略。
- 隐私：简历/JD 明文日志清理、脱敏存储、访问审计。
- 限流：按 IP、用户、接口类型限制 LLM/OCR 调用，避免成本失控。
- 观测：结构化日志、错误告警、外部 API 延迟和失败率指标。
- 回滚：前端原子回滚；后端保留最近稳定镜像；数据库迁移必须可回滚或可前滚修复。
