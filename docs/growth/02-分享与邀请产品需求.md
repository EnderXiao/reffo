# Reffo 分享与邀请产品需求

版本：V1.3，2026-10-19。基于 `feature/workflow-v5@1e90476` 的产品设计与研发拆单；本文新增能力均未实现。关联：[上线推广与增长方案](./01-上线推广与增长方案.md) · [首月运营执行手册](./03-首月运营执行手册.md) · [生成结果分享卡方案](./04-生成结果分享卡方案.md)。

## 1. 目标与范围

让获得价值的用户能自愿推荐工具，让朋友先看懂再创建自己的定向简历，并辨认真实推荐效果。

| 阶段 | 范围 | 开启条件 |
| --- | --- | --- |
| P0，首发必备 | 奖励邀请链接、独立免登录接收页、归因绑定、注册即时发 3 次、好友首个真实任务后邀请人发 5 次、任务级权益账本、硬预算预留与停止新绑定 | 批准预算和规则；任务级权益、幂等入账、并发上限、回滚和端到端链路全部通过 |
| P0+，补充展示 | 针对本次生成结果自动展示一条短原文、分享预览、冻结快照与撤回 | 不让用户选择或改写；原文/版本、授权、隐私提示和撤回通过；不额外调用模型 |
| P2，另立需求 | 完整公开案例、简历协作、公开内容广场、更多原生分享 | 有明确需求与独立隐私设计；不默认公开历史 |

不首发积分商城、现金返利、会员支付、公开分数排行、通讯录邀请、好友求职状态，也不因分享功能改造私有简历数据访问规则。

## 2. 三类用户故事

1. 邀请人：我想清楚告诉朋友双方能得到什么，并看到好友是否完成了领取我奖励所需的真实任务；我不需要公开简历，也不应看到好友的个人求职进度。
2. 受邀好友：我想在注册前知道自己会获得什么、邀请人何时获奖；注册后能立即使用额外权益，不被要求晒图、加群或好评。
3. 运营负责人：我想追踪奖励从绑定、到账到核销的全流程，并在预算达到硬上限时停止新增承诺，不收集简历正文来分析渠道。

## 3. P0 页面与交互

### 3.1 入口

| 位置 | 文案 | 触发与频控 |
| --- | --- | --- |
| 完成页 | “邀请好友，双方得岗位优化次数” | 成果完成后轻量入口，每会话最多主动展示一次；不拦“回首页” |
| 结果页下载附近 | “邀请好友” | 展示双方奖励条件；不影响下载和编辑 |
| 个人页 | “邀请记录” / “我的分享卡” | 可查看匿名状态、3/5 次奖励和预算活动状态；不展示好友身份或具体任务 |

当前完成页存在全屏点击返回和约 10 秒自动回首页。打开分享面板时必须暂停自动返回，操作区阻止冒泡；关闭后让用户主动返回，不在编辑/下载图片中途倒计时跳走。推荐失败不影响已完成成果。

未完成或生成失败时不主动提示分享；用户仍可从个人页推荐通用工具。未登录用户可复制无个人归属的普通推荐链接；账号推荐标识在登录后由服务端生成，不以邮箱或用户 UUID 编码。

### 3.2 分享面板

P0 面板标题：“邀请好友，双方获得岗位优化次数”。规则紧邻主按钮展示：“好友完成注册验证，额外获得 3 次；好友完成首个真实岗位简历任务后，你获得 5 次。活动奖励受总预算限制，当前是否可参与以页面状态为准。”按附件配置新客基础 5 次时，须与邀请加赠分开展示，明确 3 次是额外权益。

面板提供复制链接与系统分享。P0+ 可在权益说明下自动展示本次生成结果的一条原文：

- **复制邀请链接**：链接与邀请说明分别可复制；复制成功只提示“链接已复制”，不提示“分享成功”。
- **原文补充展示**：由系统从本次最终结果中按固定规则选取一条完整短句/要点，逐字显示；用户不能挑选、编辑或生成替代文案。预览时可保留或关闭该条原文，关闭不影响邀请奖励。
- **系统分享**：仅在当前浏览器支持时显示；调用 Web Share API 或相应平台适配，不模拟平台发送成功。

原文无法安全定位、结果版本不可核验或触发高风险信息检测时，退回只含邀请权益的通用卡。Web Share 不可用、用户取消、剪贴板无权限、图片生成失败分别提供回退。微信内置浏览器优先测试链接复制/图片预览；微信菜单分享需要另配公众号 JSSDK 与域名验证，未验收前不展示“已支持微信原生分享”。RN 分享走独立平台适配和真机验证；小程序只在实际发布后扩展，不假定 `showShareMenu` 适用于 H5。

### 3.3 生成结果分享卡与普通链接

邀请权益是分享卡主体。按用户本轮选择，生成简历原文只作为自动添加的补充信息：从本次最终输出中取一条完整短句/要点，用户不选择、不编辑，分享步骤不调用模型。用户发布前可预览并关闭该内容；只有明确保留时才写入公开快照。详见 [生成结果分享卡方案](./04-生成结果分享卡方案.md)。

| 卡片元素 | 示例/规则 |
| --- | --- |
| 邀请权益 | 好友注册额外 3 次；好友完成首个真实简历任务后邀请人得 5 次；活动预算状态与规则入口 |
| 补充原文 | 最多一条从本次最终简历输出中自动提取的完整短句/要点，原样呈现；用户可关闭，不可选择或编辑 |
| 品牌/行动 | 固定 Reffo 标识和产品入口；不额外生成发现、总结、话题或营销故事 |
| 到达 | 链接指向邀请承接页与同一已确认快照；不暴露私人历史句柄 |

卡片优先呈现权益与 CTA，原文补充不得压过奖励规则。图片独立渲染已授权快照，不截取私人结果 DOM；超出长度的原文不截断，无法找到完整短片段时隐藏补充层。

链接预览默认通用站点图；若包含原文，只能来自同一快照的已公开字段，不可动态读取任务。用户发布前同时预览图片、接收页与链接预览。部署须实际支持抓取；撤回需清理自有缓存，不能承诺收回第三方副本。

### 3.4 独立公开接收页

建议逻辑路由为 `share-entry`，部署后可映射为 `/s/<随机分享标识>`；实际正式域名未确定，本文路径为设计约定。

首屏从上到下：

1. “一个岗位，一份专门准备的简历。”
2. 三步说明和一组静态虚构示例，可选择查看详细操作。
3. “当前可生成可编辑内容，H5 支持 Markdown 下载”；产品能力变化时同步调整，不称已支持 PDF/Word。
4. “用我的简历和岗位试试”主按钮，“先看示例”次按钮。
5. 数据处理说明、隐私政策、支持入口；处理真实材料前进入正式身份与授权流程。

普通邀请链接使用上述通用页面。含补充原文的分享卡链接先显示邀请双方权益，再显示分享者预览确认保留的一条生成简历原文和产品入口；无需登录查看，不以登录解锁他人简历。好友不能访问邀请人的姓名、头像、公司、历史记录或奖励明细。页面不要求加群、关注或公开分享后才体验，不伪造 offer 背书。

分享短链失效或活动结束时，显示普通产品入口；奖励规则已结束时不展示仍可得券。仅停奖励不关闭正常产品体验。所有接收页面允许首访直接查看，不能被 `guardLandingEntry()` 无条件替换；守卫执行前先捕获有效来源并保存安全回跳目的地。

### 3.5 登录与匿名体验边界

- P0 的通用公开示例是静态、虚构内容；P0+ 接收者读取已授权快照，都不为每个访客跑模型。自己的真实材料进入已验证账号流程。
- 现有 Landing 匿名能力保留与否由发布范围决定；即便开放，也要有速率、并发与成本上限，不直接作为奖励资格。
- 登录页、验证码、OAuth 统一使用短期 `growth_context` 和站内 `return_to`。现有 OAuth 回调只保留部分 URL，不能把 ref/UTM 只放在 query 中。
- `return_to` 仅允许站内路由白名单，禁止任意外部跳转；OAuth 的安全 state 与 PKCE 等安全机制保留，不替换成营销字段。
- 访客旧成果同步到账号不能直接产生邀请奖励；必须由服务端验证交付事实、归属与非演示状态。最小首发方案只承认登录后的新真实岗位交付，不追溯无法证明的 guest 历史。

## 4. P0 归因规则

### 4.1 三个独立标识

| 标识 | 用途 | 边界 |
| --- | --- | --- |
| `campaign_id/content_id/partner_id` | 内容和伙伴的运营来源 | 允许列表，不含群成员名单或个人信息；随机 URL 参数不能控制活动资格 |
| `share_id` | 某次分享资产或推荐链接 | 服务端随机生成、不含用户 UUID；公开接口仅返回通用内容或已授权快照及有效状态 |
| `referral_code` | 推荐账号的归属引用 | 服务端维护账号映射、可停用；guest 普通链接不附个人推荐关系 |

UTM 仅供来源分析。奖励资格由服务端活动配置、有效推荐码与注册绑定共同决定，不能信任前端 `reward=true`、渠道名或客户端时间。

### 4.2 时间窗与优先级（建议初值）

1. 捕获首次有效访问，访问后 7 天内可在完成验证的新账号上绑定推荐；“新账号”必须在活动有效期内创建，且满足 `first_valid_referral_visit <= account.created_at <= verified_bound_at`。注册验证时幂等绑定，并立即发放好友额外 3 次；不能让已注册账号后来首点邀请或重新登录变成新客。
2. 注册前允许看到多个来源；推荐归属采用首个有效推荐上下文。绑定后固定，不被后续链接、登录重试或 UTM 改写。
3. 自邀、停用码、过期码不绑定；用户继续正常使用。来源字段可记录为 unknown/invalid，不编造关系。
4. 受邀好友绑定后 14 天内完成首个合格真实任务，邀请人才获得 5 次；超出窗口后不再产生邀请人奖励，好友已到账的 3 次不追扣。
5. 跨浏览器/设备不偷偷合并。用户可在账号创建前的注册步骤主动输入推荐码，服务端当时建立有效上下文；仍须检查时窗和新客状态，不能在账号创建后补录或回填伪造访问时间。已有合法上下文则沿用首个，注册/验证重试不改写归属。

每次活动使用独立规则版本。不能把活动开始前已注册的账号追溯认定为新客，也不能追溯不明确的奖励承诺。

来源分析分别保留 first-touch 和 last-non-direct；推荐关系独立统计。一个用户可以来自内容，后由朋友推荐，但新增账号的邀请归属只能有一个。报告要说明口径，合计用户时去重。

### 4.3 存储和用户控制

推荐上下文只保存随机标识、服务端可校验签名/句柄、活动版本、有效期、站内回跳路由；不保存简历/JD正文、邮箱、访问 URL 全量 query 或 OAuth token。使用项目跨平台 storage 封装。

用于奖励履约的最小关系记录与可选运营统计分别说明处理目的。用户拒绝可选统计时仍能看示例和使用工具；没有足够授权或标识时标为不可归因，不用指纹补洞。建议初值：未绑定上下文 7 天、可选原始行为事件 30 天；为队列统计及时生成不含正文的首次激活、有效访问、绑定与交付派生事实，并按复核窗口保留。分享草稿只保存自动提取原文的结果版本与来源引用，不保存整份简历；公开快照按分享卡方案显示准确到期日并支持提前撤回。账号推荐与奖励明细保留至结算/争议所需期限；具体期限在活动发布前按实际运营义务确认并写进政策，不能无期限存放。到期删除或聚合，账号删除同步处理公开码和未绑定上下文，已承诺权益另按明确规则处理。

## 5. P0 邀请奖励与权益定义

### 5.1 为什么需要独立任务口径

现有每日“生成次数”实际由 analyze 缓存 miss/disabled 消费。复用源简历可能不再扣分析次数，匹配与生成也没有同等任务级计次。**不能只把 `remaining + 1`，也不能只给配额表加一行，就对外承诺一张“岗位优化券”。**

本期奖励开放前统一新增“岗位优化任务”权益，覆盖所有能够产生该成果的入口，而不是只限制分享入口：

- 一个 `optimization_task_id` 绑定一个账号、一版源材料和一个目标 JD；改变材料或 JD 创建新任务，重开同一任务复用已有结果。
- 按附件建议，新账号基础 5 次、邀请好友额外 3 次、邀请人获 5 次均作为任务权益分别入账；基础 5 次需与全局新客权益确认后再对外展示，不能混同当前每日分析额度。
- 新任务开始前原子预占权益；缓存命中也检查任务权益，防止绕过。权益类型、有效期、扣减顺序在活动规则中透明展示。
- 预占 → 合格交付核销；失败、超时且确认没有交付时释放。重试沿用同任务，不重复扣减。晚到响应与退款竞争通过任务状态机/事务判定，不出现“免费交付后还可再花同一券”。
- 每张券只覆盖一个任务的必要分析、匹配与简历生成；重读结果不扣，更换 JD/材料须新任务。本期不承诺额外面试额度或延长现有运行上下文期限；面试建议按其单独公布的使用、频率与成本规则执行。
- 独立的模型调用频率/并发/成本限制继续存在，并提前说明暂时不可用状态。旧分析配额的展示和执行不能与新任务权益重复扣费；建议在新的一天灰度切换，历史分析计数保留审计，不追扣老任务。

任务级权益是奖励活动的上线阻断项。若暂不完成权益改造，邀请奖励保持关闭，不得用现有每日分析配额冒充邀请任务权益。

### 5.2 奖励规则与结算

| 项目 | 首发方案 |
| --- | --- |
| 资格 | 已验证新账号、有效且唯一推荐绑定、非自邀、非示例；每个新账号最多绑定一次并领取一次邀请加赠 |
| 好友奖励 | 注册验证且邀请绑定成功后，好友立即获得额外 3 次岗位优化任务；按附件保留的新用户基础 5 次另行入账，不与邀请奖励混算 |
| 邀请人奖励 | 好友在绑定后 14 天内完成首个真实 JD 的合格简历任务交付后，邀请人获得 5 次岗位优化任务 |
| 达标事件 | 服务端生成链路确认完整交付，落 `activation_receipt`；不依赖客户端保存历史、分数、下载或正面评价 |
| 邀请数限制 | 不设邀请人个人名额/次数上限；活动总奖励预算设硬上限，按每个有效绑定最多 8 次增量任务权益的最坏履约成本预留 |
| 硬预算 | 邀请增量权益的活动总预算记为 `B_invite`，覆盖额外 3 次与 5 次；附件建议的新客基础 5 次按全局获客成本另列。单任务最大可变成本记为 `C_task_max`，绑定时预留最多 `8 × C_task_max`。无法在调用前限制单任务成本时不得启动活动 |
| 有效期 | 建议奖励自发放起 30 天有效，最终到期时间按服务端时间计算并在领取前展示；不得沿用无明确规则的代码默认值 |
| 既有承诺 | 注册绑定须在同一事务确认预算、锁定邀请关系、发 3 次并预留邀请人的 5 次；预算不足时不建立有奖关系，普通注册仍可继续 |
| 退出 | 预算达到硬上限后停止新的有奖绑定，保留既有绑定、待核销与已发奖励的履约预算；作弊可按已公布规则冻结并提供申诉 |

预算预留要覆盖已发给好友的 3 次，以及好友达标后邀请人应得的 5 次。好友未在窗口内完成任务时，按公开规则处理剩余预留；若已发的 3 次不可撤销，则该部分成本不得提前释放。活动停止新绑定后，已有好友仍可在其 14 天窗口内达标并触发邀请人奖励。

`C_task_max` 须由最大输入长度、模型调用次数、输出长度、OCR 页数和有限重试共同约束，且每次调用前检查剩余预算；P95 加余量仅用于预测，不能代替硬上限。核销中保留剩余执行预算，任务完成后按实际成本结转；已发未核销权益持续计入未履约敞口。无法保证预算与履约承诺一致时，不启用奖励活动。

活动升级不能静默改变已绑定账号的规则。注册前展示双方获权条件、活动总预算规则、有效期、任务口径、数据处理和支持方式；与账号绑定时记下规则版本。权益与正面评价、营销订阅无关。

### 5.3 邀请状态机

```text
valid_visit → verified_bound → invitee_3_granted → awaiting_first_delivery
                                             └────→ inviter_5_qualified → inviter_5_granted
终态/分支：expired / ineligible / review_required / rejected / disabled_before_binding
```

只给邀请人展示“待完成 / 待核查 / 已发放 / 未满足规则”，不显示受邀人邮箱、姓名、简历、公司、具体访问时间或任务内容。可用匿名流水区分记录；不提供逐个朋友的实时求职跟踪。

权益流水：好友 3 次为 `issued → available → reserved → consumed`；邀请人 5 次在好友首任务完成前为 `qualified_pending`，达标后 `issued → available → reserved → consumed`。释放返回 `available` 或已到期的 `expired`；撤销追加冲正，不直接删除流水。发放、预占、消费、释放均有唯一幂等键。

### 5.4 可信交付与 guest 边界

在服务端 generate 完成门禁并持久化结果后写入可恢复的 receipt，包含账号、内部任务/运行引用、真实/演示类别、交付状态、时间和规则版本。不得由前端提交 `delivered=true`。

首份激活唯一约束以账号为单位；同一任务网络重试、缓存复用和重复回调只产生一条。邀请达标写状态、发双方权益使用事务或幂等 outbox；中途崩溃可重放，不会一方多发、一方漏发。

当前历史保存接口接受客户端上传的正文、分数和 process_result，不能作为可信奖励证据。guest owner 不能直接归到某个新账号；本地同步、客户端打勾和截图均不补造 receipt。将来若支持 guest 交付转账号，要另增一次性服务端领取凭据和所有权证明，本期不要求。

### 5.5 最小反滥用与成本控制

服务端核验邮箱验证状态、账号创建时间、唯一绑定/首份激活；关键接口限频和限制并发；活动层设置硬预算总上限、单任务成本上限、开关及异常待核查队列。不设单个邀请人的奖励名额上限；不为此新采集通讯录、身份证或跨站设备指纹。

IP 仅作短期风险线索，不以校园/公司同网一刀切拒绝；不把原始简历或跨用户简历哈希另建反作弊库。已确认无效的合格事件可撤销资格，但用户正常基础使用不因此自动封禁。

保持接口集中于 service、路由层校验和 repository 持久化，不把来源/奖励判断散入页面。后端响应延续现有 `ApiResponse<T>`。

## 7. 事件字典与报表

| 事件 | 来源与触发 | 用途/限制 |
| --- | --- | --- |
| `share_entry_viewed` | 客户端入口真正可见 | 推荐入口曝光分母 |
| `share_action_started` | 点击复制/图片/系统分享 | 记录 action，不等于实际发送 |
| `share_asset_prepared` | 剪贴板成功或图片已准备 | 图片下载只记发起，不声称已保存 |
| `share_excerpt_auto_prepared` / `share_excerpt_kept/hidden` | 系统生成本次结果原文补充项、用户预览后保留或关闭 | 只记录内部任务引用、结果版本和状态，不记录原文；无可用片段时记为 unavailable |
| `share_snapshot_published/revoked` | 服务端发布/撤回成功 | 公开不等于实际转发；到期另记状态 |
| `share_landing_viewed` | 浏览器页面可见确认 | 与服务端 token 请求区分，社交预览爬虫不计人访 |
| `example_viewed` / `real_task_started` | 客户端行为 | 示例与真实任务分流，后者用服务端 journey/run 校验并关联权益任务 |
| `signup_verified` / `referral_bound` | 服务端认证与绑定成功 | 邀请漏斗，拒绝伪造登录事件 |
| `optimization_delivered` | 服务端可信交付 | 真实/演示明确区分，run/task 去重 |
| `result_presented` / `history_saved` / `export_started` | 页面真实展示、保存回执/下载发起 | 与交付、质量和实际投递分开 |
| `usability_feedback` | 用户可选反馈 | yes/needs_work/not_applicable，非奖励条件 |
| `invitee_bonus_granted` / `inviter_reward_qualified/granted/reversed` | 仅服务端 P0 | 区分好友注册即得 3 次与好友首任务后邀请人得 5 次 |
| `benefit_reserved/consumed/released/expired` | 仅服务端 P0 | 追踪实际成本、硬预算使用量与未履约敞口 |

通用字段仅允许：事件 ID、服务端时间、随机会话/短期匿名标识、经授权的内部账号标识、平台、模板/活动/内容/伙伴/推荐引用、内部 task/run 引用、状态码、规则/实验版本。账号标识只在受控内部分析使用。

禁止记录：简历/JD/面试原文、姓名、邮箱、电话、公司、文件 Base64、token、完整 URL/query、任意自由文本反馈。事实错误反馈若需原文，走用户另行选择的私密支持流程，不放增长事件流。

客户端事件按事件 ID 幂等、重试有上限；离线补传明确发生时间与接收时间，奖励窗口只由服务端可信事实决定。服务端记录与客户端事件可以缺失，报表展示缺失率，不以匿名标识补造账号。

`K14` 报表以“本周首次激活账号”为分母，统计其激活后 14 天内产生推荐访问、最终在注册及交付窗口内带来的有效新激活；要等最后一次访问的 7 天注册 + 14 天交付窗口成熟才定稿，之前均标 provisional。单账号最晚为首次激活后 35 天，整周队列最晚约入组首日后 41 天成熟；派生归因事实须覆盖该窗口及复核期。可另报 14 天已实现值，但不能与成熟值混用。

## 9. 验收场景

### 9.1 P0 必须通过

| 场景 | 预期 |
| --- | --- |
| 新设备首次点外部分享链接 | 直接看到接收页；有效来源不被首访守卫丢弃 |
| 邮箱注册/验证码/OAuth 后返回 | 回到约定的站内创建步骤，保留一次合法推荐上下文；重复回调不重复绑定 |
| 多推荐链接、自邀、旧账号、过期码 | 首个合法上下文按规则绑定；其余不覆写、不发新客资格；正常使用继续 |
| 无登录看示例 | 无真实履历暴露，无必需的模型调用；拒绝可选统计仍可浏览和继续 |
| 从私人结果进入普通推荐并抓取响应 | 页面、接口、图片、二维码、OG 元数据都无私人履历或句柄；P0+ 只能读取其确认的字段，追加专项验收全部通过 |
| 完成页打开面板超过 10 秒 | 不自动离开；按钮不触发全屏回首页，关闭后成果仍在 |
| 取消系统分享、剪贴板拒绝、图片失败 | 明确状态与复制/预览回退；不记“已发送”或发奖励 |
| 机器人预抓取、重复刷新、批量事件 | 预抓取不记人访或注册；事件幂等限频，不产生可信交付 |
| 客户端伪造历史、评分或 delivered 事件 | 不产生 activation_receipt，不改变邀请资格 |
| 访客旧成果同步到新账号 | 可按现有同步体验保存，但不自动算真实推荐激活；需登录后合格新任务 |
| 任务已交付但客户端断网 | 服务端交付事实保留，客户端展示/下载可能缺失；报表能辨认差异 |
| 模板下线/链接失效/运营活动停止 | 提供普通产品入口，状态真实；不暴露私人数据或承诺已关闭奖励 |

### 9.2 邀请奖励闭环必须追加通过

| 场景 | 预期 |
| --- | --- |
| 同一账号首次交付被多次重试/回调 | 一次合格激活，最多一组双方发券，崩溃重放能补齐 |
| 有效新好友注册绑定 | 基础新客权益按已公布规则发放；邀请额外 3 次立即到账，账本可查且重复请求不重复赠送 |
| 好友首个真实任务交付 | 服务端确认后邀请人获得 5 次；客户端伪造交付、演示任务或重复交付不触发 |
| 同账号同时启动两任务仅有一张券 | 原子预占最多允许一个；缓存 analyze 不绕过新 JD 权益 |
| 生成失败、超时与晚到响应竞争 | 状态唯一收敛；无重复扣券、重复退款或退款后重复免费交付 |
| 换 JD、改源材料、复用同任务 | 前两者新任务按规则扣额，最后者重读不扣；券不增加面试额度，面试遵循独立限制 |
| 活动预算接近/达到硬上限 | 按并发原子预留；预算不足时停止新的有奖绑定，普通注册可继续；既有绑定仍按时履约 |
| 同一邀请人连续邀请、多好友并发注册 | 不设邀请人数上限；仍按总预算原子预留每个关系最多 8 次增量权益，不超出活动硬预算 |
| 好友注册后未完成任务、跨窗口完成或奖励到期 | 好友已领 3 次不追扣；只有绑定后 14 天内首任务触发邀请人 5 次；预留按规则释放或履约 |
| 单任务成本上限将被突破、预算不足以启动下一调用 | 调用前拒绝/暂停新的权益消费；已绑定奖励使用预留预算履行，告警不代替硬校验 |
| 准时跨日/月、券临近过期、规则改版 | 上海日/月边界正确；预占与有效期可解释；旧队列按绑定版本 |
| 同公司/校园 IP、人工复核和申诉 | 不只因共享网络拒绝；展示可理解状态，不暴露其他账号信息 |
| 撤销作弊资格、活动紧急关闭 | 追加可核对冲正；普通推荐可用；非作弊用户既有承诺不被批量抹掉 |

## 10. 发布与回滚

开关至少分离：`share_entry_enabled`、`result_excerpt_share_enabled`、`attribution_enabled`、`real_guest_processing_enabled`、`referral_reward_enabled`。奖励首发须由服务端活动配置控制；硬预算到达时自动停止新绑定。关闭邀请奖励不影响普通产品注册；关闭新增绑定不取消已经承诺的权益。

归因或奖励入账失败时暂停新有奖绑定，保留队列与账本做幂等补偿；不得继续展示无法兑现的奖励。权益核销不可用时不启动需要扣券的新任务，用户仍可查看已有结果。P0+ 原文补充层失败时可单独关闭并退回权益卡；疑似泄露时关闭相关公开读取并清理自有缓存。

运营每周核对：有效访问与绑定、首次交付、发券与核销、实际成本与待履约敞口；对不一致项有负责人，不通过改报表掩盖漏发。增长功能的数据目的、存储期限、活动规则、支持入口及实际功能说明须与正式协议/隐私文案一致，再面向用户开放。
