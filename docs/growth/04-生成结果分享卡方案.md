# Reffo 邀请奖励分享卡与生成结果补充展示方案

版本：V1.3，2026-10-19。基于 `feature/workflow-v5@1e90476` 的产品方案，新增能力待实现。关联：[分享与邀请产品需求](./02-分享与邀请产品需求.md)。

本方案以邀请奖励为主：好友注册验证后获得额外 3 次岗位优化任务，好友完成首个真实任务后邀请人获得 5 次。分享卡可以自动展示本次生成结果中的一条原文作为补充；原文不另行输出、不由用户挑选或改写，用户可预览后关闭。

## 1. 产品定义

分享卡的主体是**邀请权益和邀请入口**。用户通过链接邀请好友，好友注册后立即获得 3 次岗位优化任务；好友完成首个真实岗位简历任务后，邀请人获得 5 次。奖励与是否公开简历片段无关，也不以实际转发行为结算。

简历原文是可选的补充证明，直接来自这位用户当前这次最终生成结果。不同结果可能出现不同内容，也允许重复；不承诺每次都独一无二。没有合适原文时，卡片只展示邀请权益。

## 2. 卡片内容

| 内容 | 规则 |
| --- | --- |
| 邀请权益 | 说明好友注册额外得 3 次、好友完成首个真实任务后邀请人得 5 次，并提供活动规则入口 |
| 补充原文 | 最多一条从本次最终简历结果自动提取的完整短句/要点，逐字呈现；用户不能选择、编辑、拼接或改写 |
| 品牌与行动 | 固定 Reffo 标识和产品入口/二维码；不另写针对该用户的营销文案 |

默认不展示用户姓名、头像、目标公司/岗位、简历评分、原始简历对照、生成解释、标签、提问、用户感想或其他简历章节。卡片优先保证权益与规则易读；原文最长 80 个字符，超长不截断、不浓缩、不改写，直接退回无原文版本。

### 示例

假设某次生成的最终简历包含：

> 负责活动报名流程设计，并整理现场问题记录。

系统按固定提取规则自动取出这条完整原文，放在双方邀请权益下方。此处为虚构示例，不代表所有用户都会生成相同内容。换一个人或目标岗位，自动补充的原文可能不同；若没有可用内容，则不展示原文，邀请卡照常使用。

## 3. 用户流程

1. 简历生成成功后，结果页显示低打扰入口“邀请好友得优化次数”。保存、编辑和下载仍是主要操作。
2. 面板先展示邀请规则与双方权益；好友注册后得 3 次，好友首个真实任务完成后邀请人得 5 次。活动剩余预算不足时，明确显示暂不可参与有奖邀请。
3. 系统从本次最终简历结果按固定规则自动提取一条完整短句/要点。用户无需选择或输入任何简历内容。
4. 分享前展示最终邀请卡和接收页预览，清楚说明原文会向持有链接的人公开。用户可确认保留该条原文或关闭原文补充；若关闭，仍可分享纯邀请权益卡。
5. 用户确认后，服务端发布只含邀请信息和已确认补充原文的不可变快照，生成随机链接/二维码；随后可复制链接、下载图片或使用当前平台支持的系统分享。
6. 用户可在“邀请记录/我的分享卡”查看奖励状态、复制链接或撤回分享卡。简历结果后续编辑或重生成，不静默修改已发布快照；新结果需重新打开分享预览并确认。

打开分享流程时暂停完成页自动返回，操作区域不触发页面返回；分享失败不影响简历生成、保存或下载，分享动作本身不发放奖励。

## 4. 用户分享动机与验证假设

主要动机来自清晰的互惠权益：好友注册后立即拿到可用次数，邀请人仅在好友真正完成一次岗位简历任务后获得奖励。原文补充的作用是让朋友看到这位分享者确实使用了 Reffo，不承担主要转化动机。

该动机仍需上线验证：奖励可能提升邀请行为，但也可能带来低意向注册、刷量和预算消耗；受邀好友是否完成任务才是质量信号。原文补充还会增加隐私顾虑，因此必须可关闭，不能成为领取奖励的条件。首轮重点观察：

- 邀请链接到注册、受邀好友首个真实任务、邀请人 5 次到账及双方权益核销的转化。
- 用户是否愿意在已清楚看到权益条件后主动分享；复制、下载或系统分享调用不等于实际发送。
- 自动补充原文被预览后保留或关闭的比例，以及隐私顾虑和接收者理解情况。
- 奖励异常、预算敞口和支持工单是否在硬预算内可控。

优先验证用户自愿私聊给正在求职的朋友，不要求公开发帖。奖励只是邀请理由，不要求晒图、加群、好评、关注或提交聊天记录。首发小流量能验证规则可理解、流程可用和成本受控，不足以证明长期自然裂变或奖励带来的净增量。

## 5. 内容来源与处理边界

| 数据 | 设计要求 |
| --- | --- |
| 本次生成简历 | 从该任务的最终生成结果中按固定规则自动提取一个连续完整原文；来源、账号和成果版本由服务端核验 |
| `changes_summary` | 当前是结果正文摘录/展示数据，不作为改写前后差异、发现总结或额外卡片文案 |
| 结果编辑 | 分享内容必须精确对应用户预览的最终结果版本；结果更新后旧分享保持冻结，新版内容需重新生成预览并确认 |
| 原始简历、JD、Agent 内部分析 | 不作为卡片内容，不进入公开快照、图片、链接预览或增长事件 |

卡片文字必须是结果中的连续原文。首版采用确定性解析：从本次最终简历 Markdown 的工作、项目或实习经历中，按文档顺序寻找不超过 80 个字符的一条完整要点；排除明显的邮箱、手机号和网址。用户在预览中核对其余可能识别身份的信息，选择保留或关闭，不提供替换候选。系统可做字符串定位、版本校验和权限校验，但不能重写、概括、润色、截断或拼接。无法核验来源、未找到完整短句或检测到高风险内容时退回纯邀请卡。

## 6. 公开边界与快照生命周期

- 用户明确授权的仅是其预览后保留的这一条自动提取内容，不代表授权公开整份简历、JD、姓名、头像、账号、来源记录或其他生成结果。
- 图片、公开页和链接预览只读同一份显式确认的白名单快照；不通过私人历史接口动态取数，不暴露内部记录 ID、账号 ID、源文件路径或完整生成结果。
- 卡片和链接默认可被拿到链接的人查看或转发，不描述为“仅好友可见”。发布前展示最终内容和这一边界。
- 公开快照使用不可猜随机 token，允许用户提前撤回并设置清晰的到期时间。撤回或到期后，自有页面、图片端点及缓存一并失效；已下载图片、截图和第三方预览缓存无法保证收回，需提前告知。
- 增长事件、日志和运营报表不记录卡片正文、简历/JD 内容或截图。分享卡不得成为公开案例库或默认可索引的人物主页。
- 自动检测联系方式等显性标识；姓名、雇主/学校、项目名、客户、业务机密、精确时间和业绩数字仍可能无法可靠识别，故预览页须展示原文并提醒公开范围。用户可关闭补充内容，但不能挑选替代内容。
- 私有 history RLS、Storage 隔离与现有授权不因分享而放开。

## 7. 研发范围与事件

邀请奖励卡是 P0 主路径。自动原文补充层为 P0+，包括确定性短句提取、结果版本核验、简洁卡片渲染、公开预览与确认、冻结快照、随机链接、我的分享、撤回/到期及图片缓存失效。

分享流程不需要候选生成、额外模型调用、来源包、对照核验或文案编辑器。服务端根据授权任务和结果版本自行提取或校验片段，不接受客户端任意文本作为生成结果。先确认当前结果是否有可信的版本引用；无法证明片段来自本次最终结果时只开放纯邀请卡。

建议事件：`share_entry_viewed`、`share_excerpt_auto_prepared`、`share_excerpt_kept/hidden`、`share_previewed`、`share_snapshot_published/revoked`、`share_action_started`、`share_landing_viewed`。仅记录内部任务引用、结果版本、状态和活动版本，不记录文本。页面真实可见与服务端 token 请求分开统计，预览爬虫不计作真实接收者。

## 8. 首轮验证

先用虚构材料完成自动提取、预览、保留/关闭、发布、接收和撤回全流程。邀请奖励闭环通过硬预算与账本验收后小流量开放；原文补充权限、快照和撤回未通过时保持关闭，不阻断邀请奖励。

前 7–14 天记录邀请曝光、链接发起、有效注册、好友首个真实任务、邀请人奖励到账与核销、预算预留/释放、用户自报发送和接收端合格激活。原文补充另看自动提取成功率、预览后保留/关闭、隐私顾虑；其中约 3 名用户以相同履历尝试两个不同 JD，观察自动呈现的原文是否来自各自结果并自然产生变化。

继续投入的门槛先看奖励承诺零超发、预算预留与账本对得上、真实任务可归因且无严重隐私问题。原文补充若大多被关闭或引起明显隐私顾虑，优先移除补充层；不能追加生成文案或强制用户公开来抬高分享率。首轮样本只是流程与风险检查，不作行业基准或增长因果结论。

## 9. 最小验收

| 场景 | 预期 |
| --- | --- |
| 不同用户或不同 JD 生成不同结果 | 自动呈现的原文严格来自各自最终输出；内容可不同，也允许相似 |
| 同一段结果多次打开分享流程 | 不触发额外模型调用；同一版本呈现稳定 |
| 用户关闭原文补充或取消分享 | 不创建含原文的公开快照；纯邀请卡仍可分享，原结果使用不受影响 |
| 自动提取内容过长或含显性标识 | 不截断，退回纯邀请卡；预览可关闭其他可能识别身份的内容 |
| 用户编辑/重生成结果 | 已发布卡片维持原快照；新版须重新提取、预览并确认 |
| 未登录接收者/预览爬虫 | 仅读取已确认快照；不访问私人历史；爬虫不计真实到访 |
| 撤回、到期、删账号 | 自有页面、图片直链及缓存按状态失效；外部副本限制事前告知 |
| 接口、日志、埋点抓包 | 仅含确认的片段和必要状态；无全文、候选片段、内部来源包或正文事件 |
